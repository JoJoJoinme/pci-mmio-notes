## 地址有三种含义

| 对象 | 本文地址含义 | 读取方式 |
| --- | --- | --- |
| libvmkctl.so | ELF 链接虚拟地址 | 加载基址不在本文假定；不能直接当运行进程地址 |
| k.b00 解压出的 vmkernel | ELF 链接虚拟地址 | 本文做静态映像核对，不声称已经设置或命中运行断点 |
| PCIPassthru 可重定位模块 | `.text` 段内偏移 | 小地址不是宿主机器当前的绝对地址 |

每个切片另有 `startFileOffset`。它通过所在 section 的 `sh_offset + address - sh_addr` 得出，可以从原文件定位字节。结束地址均为不包含该地址的上界。

## 为什么有的 call 看上去跳到下一条指令

PCIPassthru 是可重定位 ELF。未装载时，外部调用位移可以仍为零，所以原始反汇编会显示 `call 下一条地址`。真正的外部目标由 `.rela.text` 中的符号和 addend 指定。本文保留原操作数，同时在分号后展示 `REL` 解析；不会把装载前的占位值冒充实际调用目标。

libvmkctl 的外部调用一般先到 PLT，再由 GOT 对应的重定位指向目标符号。例如，正文 A01 的 `call 0x381390` 通过 PLT/GOT 解析为 `SysinfoUtil::SysinfoGet`。它不是通过函数附近恰好有某个字符串猜出来的。

## 指令与数据的最低阅读约定

| 形式 | 本文如何解释 |
| --- | --- |
| `cmp x, y` 后 `je` | 相等才走该跳转；不相等走下一条 |
| `test al, al` 后 `jne` | AL 非零走该跳转 |
| `mov ..., [reg+offset]` | 读取对象字段；字段名称必须另找写入者或调用证据 |
| `mov [reg+offset], ...` | 写入对象字段；不能据此声称已执行设备 DMA |
| `cmovbe` | 无符号小于等于时选择另一值 |
| `call [rax+offset]` | 间接调用；需要 vtable/分发表重定位才可命名目标 |
| `xor eax,eax` | 清零返回寄存器；成功还是 false 要看该函数的返回语义 |

当前调用点通常用 RDI/RSI/RDX/RCX 等寄存器传参。文中会明确说明当前寄存器装的是什么，不要求读者仅靠寄存器名称猜对象身份。

## 证据怎样分层

1. **直接指令事实**：比较、跳转、读写偏移、符号重定位。
2. **控制流解释**：把这些指令整理为条件、循环或数据传播；保留前置条件和例外分支。
3. **运行对应**：引用已有 task、日志和映射采样，确认实际实验走到了有关路径。
4. **未闭合部分**：调度排序、所有 hostd 调用、完整回滚和物理硬件行为，没有用推测补成事实。

GNU objdump 与 Capstone 独立核对了本套切片的指令边界、原始字节和直接跳转目的地。它们一致不等于所有语义推断自动正确；因此解释仍逐段写出。[独立核对回执](evidence/objdump-verification.json)

## 这套文档怎样避免看起来有证据却无法审查

每段代码有稳定切片编号。单独的 `.asm` 文件、机器可读记录和正文均由相同切片数据生成；离线程序检查正文中的代码是否与记录逐字一致。持有对应合法 ELF 的复核者还可以重新导出并运行第二套解码核对，步骤见 [08 复核与未知项](08-reproduce-and-unknowns.md)。

切片中跳到窗口外的目标，会保留其地址；正文不把两个不连续窗口假装成连续代码。异常构造等大段 C++ 通用代码省略时会说明。发布包包含相关判定窗口，不包含整个 VMware 库或内核的二进制和全量反汇编。
