# VMware 传统 PCI 桥直通：问题归因与新版本复核

测试日期：2026-11-13（Asia/Shanghai）。

**工程判断更偏向 ESXi 普通 FPT 路径的逻辑/兼容性缺口，当前证据不支持“某一张网卡坏了”的解释。** 已测 ESXi 8.0 U3k 和 ESX 9.1.0.0100 都继续复现；在 9.1 中改用原生 PCI 的 e1000 模型仍复现。此结论限定于本合成桥场景，不等于 Broadcom 已确认的缺陷编号或所有真实硬件的支持结论。

直白地说：A、B 的配置地址不同，但桥让它们共用一个内存访问身份。处理 A 时，VMware 已经把这一组关联到目标 VM；处理 B 时，却又要求 B 尚未关联任何 VM，于是把同一 VM 自己建立的关联也拒绝了。换成 PCIe root port 后，两项有独立身份，初始化 A 不再提前改变 B 的这项状态，所以前序对照能够成功。这是避开失败路径，尚未修好原来的共享桥场景。

## 哪些新版本实际测过

| 版本 / build | 设备模型 | A、B 单独启动 | 同 VM A+B / B+A | 域检查日志行 |
| --- | --- | --- | --- | --- |
| 8.0 U3b / 24280767，前序基线 | e1000e | 都成功 | 都失败 | 5294 |
| **8.0 U3k / 25595708** | e1000e | 都成功 | 都失败 | 5304 |
| **9.1.0.0100 / 25433460** | e1000e | 都成功 | 都失败 | 5808 |
| **9.1.0.0100 / 25433460** | 原生 PCI e1000 | 都成功 | 都失败 | 5808 |

每个失败用例都是先登记者成功、后登记者触发相同检查；交换配置顺序后，失败对象也交换。任务、最终电源状态、日志与只读 VT-d 表采样分别保留，未把配置保存成功当作开机成功。

这里确实出现过“第一项登记成功、第二项失败”的中间状态，随后整个 VM 开机回滚。这与主机侧“启用直通是否可能只成功一半”是不同问题；本轮没有向主机启用操作注入故障，也没有据此证明主机操作具有原子性。

结果见 [8.0 U3k](raw/u3k/u3k-default-results.json)、[9.1 e1000e](raw/esx91/esx91-default-results.json)、[9.1 原生 PCI 控制](raw/esx91-native/esx91-nativepci-results.json)。前序基线与 PCIe 成功对照见[原报告](../vmware-legacy-bridge-cause-20261112/README.md)。

截至本次查询，Broadcom 列出的 8.0 U3 分支最新补丁是 U3k；9.1 分支已到 **9.1.1.0100 / 25782009**。后者没有取得介质，**未进行二进制或运行验证，不能声称它已修复或未修复**。[官方 build 列表](https://knowledge.broadcom.com/external/article/316595/build-numbers-and-versions-of-vmware-esx.html)

## 为什么判断软件侧，而非设备损坏

1. 失败跟随第二次登记，不固定跟随 A 或 B；二者各自都能启动。
2. 原生 PCI e1000 也复现，排除了仅因 e1000e 的 PCIe 模型直接挂在传统 PCI 总线下而产生该结果的解释。
3. 对应内核检查消费的是 ESXi 自己维护的域状态：`IOMMU_GetAddressDomain` 查询到一个非 VMkernel 域时返回 Success，新登记分支却只接受“无客体域”状态，因而主动拒绝。
4. 原 build 的内核静态路径把域状态的来源对应起来：第一个成员切域时，`IOMMU_SwitchAddressDomain` 找到最上层别名桥并遍历子树，更新包括另一成员在内的域字段。这个字段正是后续查询读取的字段。新版本轮核对选定的登记检查，运行表采样也显示整组切换及失败回退；没有声称逐一还原了新版所有底层函数。

因此，本次直接失败可以由软件状态与控制流解释，不需要假定第二个设备先返回了硬件故障。仍未验证真实网卡的持续 I/O、复位质量及物理平台兼容性；“启动失败归因于软件路径”不等于完整的设备健康认证。

## 汇编能还原到哪里

依据 exact-build 符号、重定位、分支与运行证据，可以把相关新登记路径概括为下面的等价流程。名称是说明性写法，不是取得了 VMware 源码：

```text
登记单个 Function：
    检查设备身份、host owner 和依赖设备的 owner
    按该设备地址取得/创建登记对象
    若进入普通新登记的域检查分支：
        查询该设备当前的域
        若不是“无客体域”：警告、清理、失败
    继续该设备的登记和初始化

切换 DMA 域：
    找到该设备的最上层别名桥（没有时用设备自身）
    遍历作用范围内的设备，更新它们的域状态
```

冲突是：**上层登记按单个地址区分新旧，底层切域按共享单元生效。初始化 A 已经改变 B 的域状态，但 B 的新登记仍要求未分配。** 同属一个 VM 可以满足 owner 相容性，却不能自动改变另一条状态检查的前提。

三份实际模块都保留该条件，且运行日志行与静态提取值对应。[U3b 静态核对](static/24280767-guard.json)、[U3k 静态核对](static/25595708-guard.json)、[9.1 静态核对](static/25433460-guard.json)

新版模块及函数字节布局并非与旧版完全相同。这里核对的是选定分支和对应运行行为；没有凭“还能搜到相同字符串”就认定整个实现没变。

FPT 的前置回调包含依赖、所有权及设备标识检查。分发表也有 UPT、MPT 等不同实现，部分分支的域前提不同；这不代表存在一个可用于普通 PCI 设备的“跳过检查”修复开关。本轮没有改写这些分支、关闭 IOMMU 或使用签名绕过。[回调表摘要](static/registration-modes.json)

汇编足以核对这次相关的拒绝条件、状态传播与清理路径；它不能提供完整源码注释、开发者历史决策，也不能替代所有硬件、所有直通模式和并发恢复场景的验证。

## 是有意设计，还是 bug

需要区分防护条件与最终用户场景：

- **有依据的事实：** 新登记检查明确要求设备不在客体域；底层同时存在同域复用和引用计数处理。软件不是完全没有共享能力。
- **合理的设计解释，但属于推断：** 新登记从未分配/VMkernel 状态开始，可以避免误接管已有客体映射或继承未知的残留状态。这个防护本身有合理作用。
- **本例的兼容性缺口：** 共享身份使前一个成员的正常初始化改变了后一个成员的状态，而普通登记流程未协调这个组生命周期。重复查询成功被直接拒绝，没有在该检查点复用“本 VM 已建立的共享关联”。
- **不能推断的厂商意图：** 这不能证明 Broadcom 有意规定“同组设备即使全给同一 VM 也必须失败”，也不能证明它是已承诺支持的真机配置上的官方缺陷。

官方文档不推荐 conventional PCI 或 PCIe-to-PCI/PCI-X 桥，并要求桥后 Functions 共同分给同一 VM，同时要求平台和设备资格认证。共同分配是必要条件，不是对任意未认证拓扑的成功保证。文档没有把本次状态冲突明确解释成一个用户必须接受的同 VM 禁止规则。[平台和设备要求](https://knowledge.broadcom.com/external/article/312208)

因此可将当前结果按**软件兼容性缺陷/实现缺口**跟踪，同时保留厂商支持边界尚未确认的标签。正确修复需要协调组内登记、激活、共享引用和释放；不能简单删除判空检查或把任何已存在域都当成成功。

## 对我们自己的实现意味着什么

共同分配给同一 VM 应是这种共享硬件身份场景的正确方向；本次失败没有推翻这个原则。它暴露的是组级资源与逐设备流程不一致的风险：**第二个设备第一次登记时，它所属的共享资源可能已经由第一个设备初始化。**

我们的实现需要能区分“同一 VM、同一地址空间的正常复用”与“另一个 VM 占用或异常残留”，并协调组内引用、失败回滚及最后一个成员退出后的释放。验收应保留传统桥共享身份场景，同时覆盖正反顺序、单项、整组、跨 VM 和中途失败；只通过 PCIe 成功对照，还不能证明共享身份这条路径正确。

这是由本次证据提出的实现与验收要求，并非已经证明我们现有产品存在相同问题，也不是宣称修改 VMware 某一个分支就能安全修好。

## 实验和证据边界

两套独立 ESXi 8.0 U3b 覆盖盘分别通过签名 profile 正常升级到目标版本。升级输入来自联想官方仓库，完整离线包与其发布的 SHA-1 一致，同时记录 SHA-256；未使用 `--no-sig-check`。重启后核对实际 build 与变化后的 bootTime，才执行测试。[U3k 升级读回](raw/u3k/upgrade-verified.json)、[9.1 升级读回](raw/esx91/upgrade-verified.json)

静态模块来自同批官方 OEM ISO 的选定 HTTP Range 内容，逐文件保存哈希和来源；没有计算完整 ISO 哈希。运行升级使用的完整离线包另作校验，二者不得混称。[介质来源](sources/media.json)

原生 PCI 控制从已经完成的 9.1 覆盖盘分支，只替换测试网卡模型。父镜像和原基础镜像在结束后哈希不变。该子覆盖盘依赖父实验盘，复现前必须核对父镜像哈希，不能在修改父盘后仍沿用旧证据。

所有开机测试为无 guest OS 工作负载的 EFI VM，使用相同桥、BDF、完整多功能标记、4 vCPU/8 GiB 外层资源及 768 MiB 全额预留的内层 VM。本轮证明配置/登记/开机行为，不证明真实 I/O 或物理平台 qualification。新版本 UI 弹窗也不在本轮证据内。

结束时各实验实例正常关闭，目标设备禁用，专用 TAP 撤除；原先运行的 Hyper-V 测试 VM 已恢复。基础镜像及原生 PCI 控制的父盘哈希保持一致。

公开包不含安装介质、VMware 二进制、完整反汇编或凭据。原始回执、表采样、带源行号的日志摘录及采集脚本由 [manifest.json](manifest.json) 绑定。

日志摘录限定在对应开机任务的时间窗内，避免把前一个失败用例的错误算到后一个成功用例。9.1 单设备成功用例在该时间窗内没有匹配筛选条件的 vmkernel 行，摘录明确记录为零；其成功证据来自任务、VMX 登记日志与映射采样，不以“未见错误日志”代替验证。
